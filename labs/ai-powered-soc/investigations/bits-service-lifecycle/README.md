# BITS Service Lifecycle Investigation

**Case type:** Windows service lifecycle / detection engineering  
**Endpoint:** Windows 11 lab endpoint (profile name generalized)  
**Stack:** Wazuh 4.13.1, Sysmon 15.21  
**Evidence window:** 21–25 November 2026 (Asia/Kolkata, UTC+05:30)  
**Disposition:** Repeated transitions are consistent with documented BITS lifecycle behavior. No malicious BITS persistence or compromise was established. Historical attribution remains incomplete.

## Executive summary

The initial Wazuh alert (rule 61104, level 3) was generated by Windows System Event ID 7040 when Background Intelligent Transfer Service (BITS) changed from Demand Start to Automatic. Similar transitions appeared repeatedly.

Microsoft documents BITS as using delayed automatic startup while jobs are active and Demand Start when no active jobs exist. A Demand Start ↔ Automatic transition is therefore not inherently suspicious.

The investigation also found a Sysmon telemetry gap: the active `RegistryEvent onmatch="exclude"` filter explicitly excluded the BITS service `Start` value. Removing only that BITS-specific exclusion and reloading Sysmon restored Event ID 13 visibility. A controlled test verified the result.

## What was established

- Wazuh rule 61104 detected System Event ID 7040 service startup-type changes.
- The active Sysmon configuration explicitly excluded the BITS service `Start` registry value.
- Sysmon Event ID 16 recorded a configuration-state change after the targeted exclusion was removed.
- A controlled `sc.exe config BITS` change generated Sysmon Event ID 1 for `sc.exe` and Event ID 13 for a registry write by `services.exe` running as SYSTEM.
- The controlled test set DWORD `0x00000002` (Automatic); restoration set DWORD `0x00000003` (Demand Start).
- A 24-hour query returned 15 Event ID 7040 transitions. Five BITS registry-write Event ID 13 records were available after telemetry was restored.

## What was not established

- The OneDrive Reporting Task ran at the same timestamp as one BITS transition, but no causal link was demonstrated.
- `csc.exe` launched from the investigation PowerShell session around another transition. The PowerShell history showed the `Get-BitsTransfer -AllUsers` investigation command starting at the same time; the temporary compiler response directory was later absent. Causation remains unproven.
- The final BITS state following the last supplied transition at 00:09:49 IST on 25 November was not provided.
- Historical registry writer attribution for pre-fix events is unavailable because the Sysmon filter suppressed those records.
- The Edge Component Updater BITS job was in Transferred state and dated 15 November. Its local downloaded file, signature, and hash were not supplied.

## Telemetry gap and repair

The active Sysmon configuration had general RegistryEvent inclusion filters for service startup values but also an exclusion matching a target ending in `\\services\\BITS\\Start`. The exclusion explained the missing Event ID 13 records.

The lab removed only this BITS-specific exclusion, retained unrelated exclusions, and reloaded the configuration. A subsequent controlled test captured:

| Time (IST) | Process Create (Sysmon 1) | Registry write (Sysmon 13) |
|---|---|---|
| 23:29:25 | `sc.exe config BITS start= auto`, parent PowerShell; interactive lab account | `services.exe`, SYSTEM, BITS\Start, DWORD `0x00000002` |
| 23:29:28 | `sc.exe config BITS start= demand`, same parent PowerShell | `services.exe`, SYSTEM, BITS\Start, DWORD `0x00000003` |

The registry writer is not necessarily the original requesting application. In this controlled example, Sysmon Event ID 1 supplied the requesting `sc.exe` process while Event ID 13 showed `services.exe` as the registry writer.

## Detection design

The intent is to retain low-priority lifecycle visibility and escalate only materially different or contextually suspicious behavior.

| Local rule | Level | Signal | Analyst action |
|---|---:|---|---|
| 100520 | 3 | Event ID 7040 for BITS | Lifecycle context; compare old/new values and job activity |
| 100521 | 3 | Sysmon 13 write to BITS\Start | Preserve writer image, user, and DWORD |
| 100522 | 12 | BITS Start DWORD is Disabled (`0x00000004`) | Validate administrative intent and application impact |
| 100523 | 7 | Explicit `sc.exe config BITS` command | Review user, parent, integrity, authorization/change record |
| 100524 | 6 | `bitsadmin.exe` execution | Inspect job owner, URL, destination, file, and state |

Rule IDs use the 100520–100524 range to avoid a collision: the existing repository's AI-SOC baseline already uses 100510 for its `whoami /all` detection.

The rules reference built-in parent IDs/groups observed in the Wazuh Windows ruleset: 61104 (System Event ID 7040), 61615 (Sysmon Event ID 13), and `sysmon_event1` (Sysmon Event ID 1). Confirm these and decoded field names against the installed Wazuh 4.13.1 manager before deployment.

**Validation status:** The XML is well-formed and the synthetic JSONL test fixtures parse. Runtime testing with the lab's Wazuh manager and actual decoded EventChannel records remains outstanding. A rule match is not proof of compromise. `bitsadmin.exe` is dual-use.

## Collector

The supplied PowerShell collector is read-only. It gathers System 7040, Sysmon 13 and nearby Sysmon 1, Security 4688, PowerShell 4104, current BITS service and registry state, and BITS-related event-channel metadata. It deliberately does not invoke `Get-BitsTransfer`.

Run from an elevated PowerShell session:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\Collect-BITSInvestigation.ps1 -Hours 24
.\Collect-BITSInvestigation.ps1 -Hours 72 -CorrelationSeconds 90
```

The collector writes timestamped JSON/CSV exports and a SHA-256 manifest beneath `C:\CyberLab\Evidence`. It does not modify services, registry values, BITS jobs, or files.

## Operational guidance

1. Verify the current BITS service and registry state before changing anything.
2. Do not disable BITS or force a startup configuration based solely on Event ID 7040.
3. Back up the Sysmon XML before editing; remove only a BITS-specific exclusion if collection of that key is an explicit requirement.
4. Avoid removing broad RegistryEvent exclusions without a documented telemetry need.
5. Validate Wazuh parent IDs and decoded fields; run `wazuh-analysisd -t` before manager restart.
6. Test both positive and negative cases with `wazuh-logtest`; synthetic fixtures are not endpoint evidence.
7. Correlate events by ProcessGuid when possible. Time proximity alone does not establish causation.
